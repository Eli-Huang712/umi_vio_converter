> 本表"收益"列一律指**节点跑满饱和后的吞吐上限影响**（集/时），这才是批量转换真正关心的指标。**单集延迟**（如 Phase 1 的 2.1×）只在"少量集要快出结果 / 交互式"场景有意义，对批量吞吐上限**无贡献**——因为饱和时并行双腕只是把同一份 GPU 工作重新调度，总量不变。

**两个贯穿全程的关键发现：**
1. **该流水线的 VIO 输出本身不是逐次可复现的**（定速回放 + 异步感知的时序敏感）——同一集重跑，位姿会变，甚至关键帧数会变。这使"逐字节一致"成为不可用的验收标准。
2. **单集耗时由不可摊销的逐帧感知计算主导**（~15s/腕），模型加载等固定开销只占 ~20s 且大部分是每进程都要重付的，因此任何"常驻/摊销"路线的天花板只有 ~15–18%。

## 1. 方法与基线剖析

### 1.1 单集耗时拆解（实测，1 GPU）

```
单集 = 左腕 build_map 38.5s ┐
       右腕 build_map 38.5s ┤ 串行
       merge(带触觉)  0.1s ┘   合计 ≈ 77s
```

每个 38.5s build_map 内部（来自 build_map 日志的 profiler "Grand total" + 感知日志时间戳）：

| 阶段 | 耗时 | 可摊销? |
|---|---|---|
| 建图计算（pose graph / 回环 / occupancy） | **~1.6s** | 否（真实计算） |
| 逐帧感知（superpoint+lightglue+stereo+SLAM，~60–94ms/帧 × ~170 帧） | **~15s** | 否（不可摊销的主导项） |
| 模型加载（perception+build_map 各自 deserialize TRT .plan） | ~5s | 是 |
| `sleep 5` + 进程 spawn + CUDA/ROS 初始化 + DDS 发现 | ~15s | 部分 |

**关键洞察**：一集只录制 ~5.6s（~170 帧），但处理要 38.5s——**时间几乎全花在感知逐帧计算 + 固定启动开销上，真正的建图数学只有 1.6s**。这直接决定了后面所有"摊销启动开销"的方案上限有限。

### 1.2 位姿正确性的验收基准

VIO 是否逐次可复现，决定了提速方案能用什么闸门验证。见 §5 的专项测试——**答案是"否"**。

|----:|----:|----:|----:|----:|----:|----:|

**结论**（严谨版；§2.2–§2.5 对"瓶颈是什么"给出实测证明）：
- **显存从不是瓶颈**（峰值 31/143 GB）——已证。
- **观测平台 ≈1190 集/时，PAR≈64 已达顶**——已证（§2.3 边际外推）。可持续推荐 **PAR=48（1077 集/时，96% 上限）**，上限 PAR=64（1188）。
- **1190 不是计算硬墙**——**实测**每集 CPU 仅 234.7 核-秒（CPU-计算上限 2945 集/时，§2.5），GPU 计算 ≥2292 集/时（§2.4），双双 1.9–2.5× 余量。**初版"CPU 核数瓶颈"据 loadavg/util 的断言不成立（§2.2）。**
- **1190 是软性瓶颈**（最可能 GPU-context 时间片串行化 + 每集启动/IO）→ **有优化空间**，先试 MPS（§2.5.1）。
- 上表 loadavg/util 列**仅作现象记录，不作饱和证据**。

### 2.1 失败尝试：PAR=64 首跑域号越界

第一次 PAR=64 用 `DOMAIN_BASE=200`，两腕/多 worker 的域号算到 200–263，**越过 ROS2/FastDDS 的 `ROS_DOMAIN_ID ≤ 232` 硬上限**，slot 33–63 的 DDS 实例秒崩（`RTPS_TRANSPORT_SHM` / "domainId over 232"），95/128 假失败。
**修复**：改 `DOMAIN_BASE=70`（域号 70–133，全 ≤232）重跑，得到上表干净数据。
**教训固化**：`DOMAIN_BASE + 并行数 ≤ 232`（批处理默认 base=70，可撑到 ~160 slot）。

## 2.2 方法学纠错：loadavg 与 util 不能证明"饱和"

初版报告据 loadavg=177/192 与 nvidia-smi util=80% 断言"CPU 瓶颈、已到上限"。**这两个都不是饱和的有效证据：**

- **loadavg** = 运行队列 + **不可中断（D 态）睡眠**的线程数。VIO 线程在等 GPU kernel、等磁盘 I/O、等 DDS 时都计入 loadavg，却**不占用 CPU 核**。所以"load 177"**不等于**"92% 的 CPU 算力被消耗"。真实 CPU 占用要看 `mpstat` 的 `%idle`→0 或 cgroup `cpu.stat` 的 busy 时间。
- **nvidia-smi util** = "有 ≥1 个 kernel 驻留的时间占比"，不是算力吞吐饱和。132 个 SM 里跑 1 个也读作 100%。真实 GPU 占用要看 DCGM `PROF_GR_ENGINE_ACTIVE` 或 accounting 的积分。

**自相矛盾之处**：PAR=64 时 loadavg 与 util **都没到 100%**，而吞吐还在涨（1077→1188，+10%）。我在 PAR=64 停下是"感觉接近了"，**从未证明曲线到顶**。因此初版"无优化空间"是未经证明的断言。以下用可靠指标重做。

## 2.3 已证（一）：吞吐上限 ≈1190 集/时，PAR=64 已达 ~100%

用**边际增益**（每加一个 worker 的吞吐增量）看饱和——它对 loadavg 缺陷免疫，纯看产出：

| PAR 区间 | 吞吐增量 | 每 added-worker | 中点 PAR |
|---|---|---|---|
| 8→24 | +439 | 27.4 | 16 |
| 24→32 | +169 | 21.1 | 28 |
| 32→48 | +194 | 12.1 | 40 |
| 48→64 | +111 | 6.9 | 56 |

边际增益随 PAR **线性下降**：`marginal(p) = -0.528·p + 35.4`，**在 PAR≈67 归零**。从 PAR=64 往上积分残余增益，**渐近上限 ≈1191 集/时** → PAR=64（1188）已是上限的 **~100%**。
**结论（已证）**：在当前单节点配置下，加 worker 到 ~64 以上**不会**再提吞吐——1190 集/时是这套配置的天花板。（初版缺这个证明，只是停在 64。）

## 2.4 已证（二）：不是 GPU-计算瓶颈（≥1.9× 余量）

用 PAR=8（每卡 1 进程）反推 GPU 计算占用：
- 每集占用一张 GPU 的**墙钟** = 8 卡 × 3600 / 275 = **104.7 s**。
- 该档 GPU util = 12% → 每集 **GPU-busy ≤ 12.6 GPU-秒**（util 高估 busy，故这是上界）。
- GPU-计算上限 ≥ 8 卡 × 3600 / 12.6 = **≥2292 集/时**，是实测 1188 的 **≥1.9×**。

**结论（已证）**：GPU 计算有 ≥1.9× 余量，**天花板不在 GPU 算力**。（显存也不是，峰值 31/143 GB。）

## 2.5 已测（footprint / roofline）：**不是**计算硬墙，1190 是软性瓶颈 → 有优化空间

用 cgroup v2 `cpu.stat`（`usage_usec` 前后取差，真实 CPU-busy，免 loadavg 缺陷）实测**单集资源足迹**（1 集两腕、GPU 7、其余 7 卡被 co-tenant 占满但 host CPU 94.8% 空闲）：

| 指标 | 实测 | 含义 |
|---|---|---|
| wall | 75.0s | ≈ 空闲基线 77s → co-tenant 几乎没拖慢（说明无明显 CUDA busy-wait 膨胀） |
| **CPU 核-秒 C** | **234.7** | 判定值 |
| 平均占用核数（C/wall） | 3.13 | 感知只是轻度多线程，非重度并行 |
| I/O | 88 MB 读 / 249 MB 写 | 每集 |

**roofline 判定**：
```
CPU-计算上限 = 192 核 × 3600 / 234.7 = 2945 集/时
GPU-计算上限 ≥ 2292 集/时（§2.4）
实测平台      = 1190 集/时
```

- **C=234.7 只是"CPU 硬墙"所需 581 核-秒/集的 40%**。→ **1190 平台不是计算硬墙**，CPU 与 GPU 计算都在实测上限的 **1.9–2.5× 之上**、都有余量。
- 稳健性：wall 75s ≈ 基线 77s，故 co-tenant 争用几乎未膨胀 C，真实 C ≤ 234.7，**只会更强地支持"非 CPU-bound"**。
- **结论翻转**：初版"CPU-bound、无优化空间"是**错的**（它据 loadavg/util，§2.2）。**实测证明存在优化空间。**

**那么 1190 平台是什么？——软性瓶颈。** 单集延迟随并行升高（77→99→158→193s @ PAR 1/8/48/64），而两种计算资源都不饱和。头号嫌疑是 **GPU-context 时间片串行化**：PAR=64 时每卡 8 进程，各自的 kernel 挤过同一 context 串行执行（聚合 GPU 计算仅 ~50%，但单进程延迟翻倍）。次要：每集进程 spawn / DDS 发现 / 模型加载，以及 I/O 突发（1190/时 ≈ 持续 82 MB/s 写）。

**这也重新定位了常驻 worker**：它的 ~18% 只摊到了"启动"那一小片；更大的 GPU-context 串行化它并没碰。

### 2.5.1 确认实验已完成（2026-07-08，H200-2 空闲节点）——**修正了本节的主因判断**

> 完整方法/证据/图见 `剖析报告.md`。**关键更正：本节此前推测的"GPU-context 时间片串行化为主因"被实测证伪**；真瓶颈是 build_map 的**单线程 ROS2 消息序列化**。

| 待补实验 | 结果 | 对结论的影响 |
|---|---|---|
| **NVIDIA MPS A/B**（N=8 同卡关/开） | 吞吐 **421→420（−0.2%，零）**、sm% 均 7% | **否决 MPS**。若真是 GPU-context 串行化，MPS 必显著提升；零提升→**证伪该假设** |
| **饱和压测 PAR=80/96** | PAR=64=**1196** 为峰；80/96=**953/936 回退**（且各 3/4 次崩溃） | "边际外推 PAR≈67 归零"由推断变**实测**；PAR>64 过订**伤吞吐+伤稳定** |
| **真实 CPU/GPU 利用率**（mpstat/dmon 稳态） | PAR=64 峰处：**CPU-busy 50%、GPU sm% 7%**——均不饱和 | 非计算硬墙，实证坐实（此前只有反推） |
| **纯净 GPU-秒 G**（空闲卡） | N=8 同卡 sm% 积分反推 **~1.2 GPU-秒/集** → GPU 上限 **~24000 集/时** | GPU 余量 ~20×，彻底排除 GPU |
| **CPU 火焰图 + GIL**（py-spy/pidstat） | build_map **GIL 串行**（top/sum=0.92），63% 时间在 `sensor_msgs/_image.py` **ROS 图像序列化** + rclpy spin | **定位真瓶颈**：每进程被单线程消息搬运钉在 ~1 核 |

**新增发现（前置报告未记录）**：容器默认 **64MB `/dev/shm`** 在 PAR≥32 时被 FastDDS 共享内存段耗尽 → ~40% 集失败且随 PAR 增长；stock `run_vio_batch_retry_parallel.sh` 靠 retry 掩盖（=白跑算力）。**修复零成本**：`--shm-size=16g`。

**据此更新的结论方向**：
- §2.5、§6、§7 中"最可能是 GPU-context 时间片串行化"应读作**已证伪**；主因是 **CPU 侧单线程 ROS 消息序列化**（每 build_map ~1 核、几乎不用 GPU）。
- §6 方案 3 "NVIDIA MPS（单节点首选）"**降级/否决**（实测 0%）。单节点首选改为 **`--shm-size=16g` + 锁 PAR=64**（零代码、回收 retry 浪费、避免过订回退），深挖上限需**削减 ROS 图像序列化**（预期 +25–50%）。
- **横向铺机器（h1+h2 ~2×）+ 存量 BACKFILL** 仍是最干净的零风险收益，不受主因更正影响。

## 3. Phase 1：并行双腕 + 可配 warmup + 看门狗 ✅（延迟/可靠性，非吞吐上限）

> **定位先行**：Phase 1 **不提升跑满后的吞吐上限**。并行双腕在节点饱和时是中性的（同一份 GPU 工作重新调度、总量不变），它的价值是**单集延迟（小批量/交互）** + **可靠性（看门狗）**；warmup 修剪只带来固定空等的小幅回收。要提吞吐上限请看 §6 的横向扩展 / BACKFILL / MPS。

### 3.1 改动
- `umi_vio_converter.py`：`--build-parallel` 让一集的**两腕 build_map 并发**跑（各自独立 ROS 域 `base+i`）。
- `_build_map_one_sensor.sh`：`UMI_PERCEPTION_WARMUP_SEC`（默认 1，原为固定 5）+ `UMI_BUILD_MAP_TIMEOUT_SEC` 看门狗（默认 300s）。
- CUDA 绑定修复：`CUDA_VISIBLE_DEVICES` 重新 export 进 tmux（tmux pane 不继承 `docker exec` 环境，否则并行时全挤 GPU0）。

### 3.2 验证（plant_collection 单集，GPU 1/2）
| | left_wrist | right_wrist | 单集延迟 |
|---|---|---|---|
| 顺序 #1 | `6f0b7c6e` n=39 | `c411f5bf` n=38 | 80.1s |
| 顺序 #2 | `6f0b7c6e` n=39 | `c411f5bf` n=38 | — |
| **并行** | `6f0b7c6e` n=39 | `c411f5bf` n=38 | **38.2s** |

当时判定：位姿逐字节一致、触觉完好（4×485）、**单集延迟 80.1s→38.2s = 2.1×**。已提交 `c88c6ea`。

### 3.3 事后修正（重要）
§5 的确定性测试证明当时的"逐字节一致"是**时序运气**（VIO 本就逐次抖动）。并行双腕**不改 VIO 算法**（各腕独立域隔离、代码与顺序版逐行相同），位姿会像基线一样逐次抖动——这不是 Phase 1 引入的。
另修：**默认改回 `--build-sequential`**——并行用 `base+i` 域，会和既有批处理驱动的 stride-1 域分配撞车致挂；并行改为**显式 opt-in**（适合少量集/交互式降延迟）。

### 3.4 有效性与定位
并行双腕**只降单集延迟，不抬吞吐上限**：在节点饱和时，两腕并发用 2× 资源换一半时间，总 GPU 工作量不变。看门狗的价值更多在**可靠性**——防止感知崩溃时 `wait_for_perception_subscribers`（无内置超时）把 GPU 无限挂死（见 §4.2 实际踩坑）。

## 4. Phase 2：常驻 worker（persistent worker）❌ 否决

### 4.1 动机与设计
目标：**摊销 ~20s/集的固定开销**（模型加载、进程 spawn、CUDA/ROS 初始化），把单集从 77s 压向 ~40s，理论上 ~2× 吞吐。
设计：保留 tinynav 的**双进程 ROS 架构**（perception + build_map，各自 executor，经 ROS topic 通信、定速回放），只把进程**常驻**——模型加载一次、每集重建"新鲜"节点（干净 SLAM 状态）。三个角色（perception 子进程 / buildmap 子进程 / orchestrator）在一个文件里，orchestrator 用行协议协调。

### 4.2 失败尝试全记录（按时间线）

**① 首跑秒崩（0.3s）——子进程缺 ROS 环境**
orchestrator 用裸 `/opt/venv/bin/python3` 启动，未 source ROS，子进程 `import rclpy/gtsam` 崩溃。
→ 修复：加 `persistent_worker.sh` 包装器 source ROS，子进程继承其环境。

**② 43 分钟 GPU 挂死——感知崩溃 → build_map 无限等待**
验证脚本误用无 gtsam 的 python 跑感知 → 感知崩 → build_map 卡在 `wait_for_perception_subscribers`（**无超时**）无限自旋，占一张卡 43 分钟。
→ 这暴露的是 tinynav 的既有健壮性缺陷，催生了 Phase 1 的**看门狗**。

**③ "perception no READY"——控制通道被日志污染**
orchestrator 从子进程 **stdout** 读 `READY/DONE` 令牌，但 perception/build_map 往 stdout 狂打 ROS 日志，把行协议冲乱。
→ 修复尝试：fd-3 + `preexec_fn` dup2 → **失败**（令牌写进了日志文件，fd 重映射脆弱）。
→ 最终修复：用环境变量 `UVC_CTRL_FD` 传专用控制管道 fd，子进程直接写该 fd。**成功**（冒烟测试通过：pair 启动、ok=1、触觉完好）。

**④ 核心失败：跨集状态泄漏（STATE LEAK）**
worker 能跑通了（ok=3/3），但位姿等价性闸门 **不通过**，且模式极具诊断性：
```
left  E1(job1): 6f0b7c6e n=39  == 基线   ← MATCH
left  E2      : 4b88102e n=74  vs 基线 n=72  ← MISMATCH，多 2
left  E3(=E1) : 292656f1 n=41  vs job1 n=39  ← 同一集，第 3 次跑多了 2
```
**第一个 job 与基线逐字节一致，之后每个 job 都漂移、且关键帧数单调增长**。persistent worker 内部是确定的（右腕 E1==E3），只是相对基线有一致的偏移——典型的**进程内跨 job 状态累积**。

针对泄漏的**四次有原则的修复，全部无效（哈希逐字节不变）**：

| # | 修复假设 | 做法 | 结果 |
|---|---|---|---|
| A | 泄漏在 ROS/DDS 保留消息 | 每 job `rclpy.init()/shutdown()`（全新 DDS participant） | **零变化**，同样错误哈希 → 排除 ROS/DDS |
| B | 泄漏在共享 TRT 执行上下文/缓冲/CUDA 图 | 只缓存只读 `engine`，每实例新建 context/buffers/graph | **零变化** → 排除 TRT 上下文 |
| C | 泄漏在进程级记忆化缓存 | 清除 3 个 `lru_cache_numpy`（`SuperPointTRT.infer`/`LightGlueTRT.infer`/`math_utils.estimate_pose`） | 先崩（见下），修好后**仍错** |
| — | （C 的附带 bug） | 用 `getattr(obj,"cache_clear")` 发现式清缓存，误触 ctypes 对象 → `LibraryLoader` 去 `dlopen` 名为 "cache_clear" 的库而崩 | 改为显式清 3 个已知缓存 |

四次修复后哈希始终是同一组错误值（`4b88102e`/`292656f1`/`be5aeee`…），说明**残留泄漏在 Python 层够不到的 native 状态里**（gtsam / CUDA / TensorRT 的 C++ 侧），非重置引擎/ROS/缓存所能清除。

### 4.3 收益实测（即便修好也不值）
| | 单集耗时（两腕） | vs 基线 77s |
|---|---|---|
| 常驻 E1 | 61.8–63s | **~18%** |
| 常驻 E2（更大的集 n=72） | ~126s | — |

与 §1.1 剖析一致：**逐帧感知（~15s/腕）主导，模型加载（~5s）占比小**，所以常驻只省 ~18%，远非期望的 2×。

### 4.4 结论：否决（Shelved）
两个各自独立、都足以否决的理由：
1. **收益天花板仅 ~15–18%**（剖析证实，逐帧感知不可摊销）。
2. **正确性无法保证**：既有 native 状态泄漏（4 修复未根除），又因 §5 的 VIO 非确定性**连"逐字节一致"的验收闸门都不成立**。
在会**静默损坏科研位姿数据**的场景，用 ~15% 吞吐换这个风险不划算。代码作为负结果参考保留在分支 `persistent-worker`（`1f0e3b9`），**未接入主流程**，默认 FULL 路径不变。

## 5. 关键发现：VIO 输出非逐次可复现

Phase 2 验证中，基线右腕位姿在不同 gate 跑之间会变（`c411f5bf` n=38 ↔ `eb46939d` n=37），触发了这项专项测试。

**测试**：同一集，同一 GPU，全新进程连跑 3 次：
```
run1  left: 6f0b7c6e n=39   right: eb46939d n=37
run2  left: 6f0b7c6e n=39   right: 10fd2263 n=37   ← 3 个不同哈希
run3  left: 6f0b7c6e n=39   right: c411f5bf n=38   ← 关键帧数 37/37/38 都在变
```

**结论**：
- 右腕**逐次给出不同的 poses.npy，甚至关键帧数都不同**（37/37/38）——**VIO 不是逐字节可复现的**。
- 根因：定速 `BagPlayer` + 异步 `MultiThreadedExecutor` 感知，`ApproximateTimeSynchronizer` 在调度抖动下会把 stereo/imu 帧配成不同对 → 不同关键帧决策。
- 左腕在这一集恰好稳定（39/39/39），是数据相关的巧合，不代表整体确定。

**影响面**：
- "逐字节一致"不能作为任何提速方案的验收闸门；正确的等价性标准是**轨迹级容差**，但容差会接受"关键帧数不同=不同的图"，这与"不改 VIO"的初衷冲突。
- Phase 1 当时的"一致"是时序运气，但其正确性论证仍成立（并行不改算法）。
- **已交付的触觉 BACKFILL 完全不受影响**——那是确定性的逐字节插入，独立核验过 0 mismatch。

## 6. 安全 × 准确的提速方案汇总

### 一等（安全，且真能抬吞吐上限）
1. **横向铺到两台节点（h1+h2）→ ≈2×**。加节点线性扩、零 VIO 改动、与单节点软瓶颈无关。**最大最干净。**
2. **存量走 BACKFILL 而非 FULL**。已有位姿的集补触觉是纯 CPU、~0.77s/集、不占 GPU、不重跑 VIO——对存量快 ~50×。
3. **NVIDIA MPS（单节点提上限的首选，待验证）**。实测证明 1190 平台是**软性瓶颈、非计算硬墙**（CPU/GPU 计算各有 1.9–2.5× 余量，§2.5），头号成因是多进程共享单卡的 **GPU-context 时间片串行化**。MPS 让多进程共享一个 GPU context、消除该串行化，**零代码、不改 VIO**。潜在收益可观（把 1190 往 2292 的 GPU 上限推），需一轮 A/B 压测确认。

### 二等（安全，小幅提速 + 提升可靠性）
4. **未来 FULL 改用 `umi_vio_converter.sh` 跑批**：一次拿到触觉 + warmup 5→1（每腕省 0–4s）+ 看门狗（防挂死拖累整体吞吐）。

### 三等（运维调参，不改代码）
5. **共享节点用 PAR=48 而非 64**（更稳、抗 co-tenant；96% 上限）。
6. **调度跳过有 co-tenant 的 GPU**（当前 GPU0 有别人的 picpp 服务占 ~12GB）；**长集优先**减少批尾空转。

### 明确不推荐（改 VIO 输出或有静默损坏风险）
- **提高 `--play_rate`**：感知逐帧计算是每集耗时的主要构成，喂更快很可能丢帧→位姿变差；且 §5 的非确定性使其难以干净验证。
- **视频解码搬 GPU（NVDEC）卸 CPU**：改解码像素→改 VIO，且动 tinynav 内部。
- **常驻 worker**：见 §4，~15–18% 且不正确。

### 有条件选项
- `play_rate` 提速**可**在团队接受"位姿本就逐次抖动"的前提下，用"rate=30 vs rate=20 的轨迹偏差是否落在 rate=20 自身抖动范围内"来放行——但这是需要拍板"抖动容差"的判断题，非纯技术安全项。

## 7. 结论

**已由数据证明：**
- **单节点观测平台 ≈1190 集/时**，PAR≈64 已达顶（边际增益线性归零于 PAR≈67，§2.3）——加 worker 不再有用。
- **1190 不是计算硬墙**：实测每集 CPU 仅 **234.7 核-秒**（CPU-计算上限 **2945 集/时**，§2.5），GPU 计算 **≥2292 集/时**（§2.4），显存峰值仅 31/143 GB——三者都远高于 1190，**都有 1.9–2.5× 余量**。
- **初版"CPU-bound、单节点无优化空间"是错的**：它据 loadavg（含 D 态等待）与 nvidia-smi util（kernel 驻留率），二者都不能证明饱和（§2.2）；实测 footprint 推翻之。
- **1190 是软性瓶颈**，最可能是**多进程共享单卡的 GPU-context 时间片串行化**（PAR=64 时每卡 8 进程，聚合 GPU 计算仅 ~50% 却单进程延迟翻倍），次要为每集启动/DDS/IO。→ **存在优化空间。**
- **现有 tinynav FULL 流水线本身不是逐次可复现的**（§5，非本次改动引入）——影响任何"逐字节一致"的验收思路。

**下一步（把软瓶颈变成收益）：**
- **NVIDIA MPS**（首选，零代码、不改 VIO）：让多进程共享 GPU context，直冲串行化根因，潜在把 1190 往 2292 上限推——需一轮 A/B 压测确认（§2.5.1、§6 方案 3）。
- **横向铺机器（2×）+ 存量 BACKFILL**：零风险、与软瓶颈无关的确定性收益。
- 定位补充：饱和压测 PAR=80/96 + 纯净 GPU-秒（需空闲节点）。

**工程交付（与上限成因无关，独立成立）：**
- Phase 1（并行双腕 + warmup + 看门狗）：单集延迟 2.1×（小批量/交互）、可靠性提升；**不提吞吐上限**（饱和时中性）；默认 sequential 对批处理安全。
- Phase 2 常驻 worker：完整实现 + 5 轮修复 + 严格验证后**否决**（~15–18% 上限 + native 状态泄漏 + 验收闸门因 VIO 非确定性不成立）。事后看：它只摊到"启动"那一小片，**没碰真正的软瓶颈（GPU-context 串行化）**——这也是它收益有限的深层原因。
