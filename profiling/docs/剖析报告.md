## 0. 摘要（先行结论）

本轮剖析用**真实**利用率指标（cgroup CPU-busy、mpstat `%idle`、nvidia-smi dmon `sm%`、同卡多进程时间线、py-spy 火焰图）回答了前置报告遗留的三个问题：

1. **瓶颈到底是什么？** 不是 GPU-context 时间片串行化（前置报告的头号假设，**本轮实测证伪**）。真正的瓶颈是 **build_map 进程的单线程 ROS2 消息序列化**——火焰图显示 63% 时间花在 `sensor_msgs/_image.py` 图像 CDR 序列化 + rclpy 事件循环，pidstat 显示该进程被 GIL 钉在 ~1 核（top/sum=0.92）。因此**每个 build_map ≈1 核、几乎不用 GPU**，节点在 PAR≈64 就卡住（远不到 192 核、GPU 仅 7%）。
2. **真实上限多高？** roofline 四线全部实测：观测平台 **1196** 集/时只是最近的 CPU 墙（**2949**）的 41%，GPU 墙 **~24000**、IO 墙 **~66500** 更远——**没有一条计算/IO 硬墙绑定**。PAR=64 是实测峰（PAR=80/96 反而回退到 953/936），前置报告"边际外推 PAR≈67 归零"由此变成实测。
3. **怎么突破、收益多少？** **横向铺 h1+h2 = ~2×（零风险）**；单节点先做 **`--shm-size=16g` + 锁 PAR=64**（零代码，回收被 retry 白跑的算力 + 避免过订回退）；深挖单节点上限需**削减 ROS 图像序列化**（火焰图指向，预期 +25–50%）。**任务书要求的 MPS A/B 已实测：收益 −0.2%（零）——被否决**，因为瓶颈不在 GPU。

关键方法学承诺（全程遵守）：**不用 loadavg、不用 nvidia-smi `utilization.gpu` 下饱和结论**（前者含 D 态等待、后者是 kernel 驻留率），一律用真实 busy 指标。VIO 非确定性 → 所有耗时取**多次中位数**。**零 VIO 代码改动**，只做外部观测与编排。

## 1. 剖析环境与执行说明

### 1.1 为什么在 H200-2 上做

任务书指定节点为 h1，但剖析开始时 **h1 的 8 张 GPU 被另一用户的作业 100% 占满**（`Jiapeilin/fastwam-robo-smoke`，每卡 ~126GB；另 GPU0 有 picpp 服务 ~12GB）。饱和扫描（PAR 80/96）与同卡多进程实验都需要**空闲多卡**，共享节点礼仪要求不抢占他人在跑的 GPU。因此按"没条件就换空闲节点"的原则，把剖析迁到**当时完全空闲的 H200-2**（8×H200 全 0%）。

迁移步骤（可复现）：
1. h1 上 `docker save tinynav_flatbuffer_saved:latest` → 59GB tar（本地盘，~96MB/s）。
2. 经 **h1→h2 内网直连**（agent-forward SSH，实测 **562 MB/s**）把 tar 流式 `docker load` 进 h2（Mac↔集群只有 9.4MB/s、跳板机 NFS 写 h2 盘 <5MB/s，都不可行 → 内网直连是唯一快路径）。
3. `:latest` 是**部署前**镜像，umi 工具只存在于 h1 运行容器层（未 commit），故把工具文件（22KB tar）经 Mac→h2 scp 后 `docker cp` 进容器，`ast.parse` 语法校验通过。
4. 从 h1 内网拷 **256 个 raw `episode.mcap`**（只拷裸 mcap、不拷 `episode/` 工作目录，确保每集都走 FULL）到 h2 scratch（14GB）。
5. **自检**：`profile_one.sh` 单集 → wall **72.4s**、median 集 **C=234.4 核-秒**、GPU mem 2437MiB、util 12%——与 h1 基线（wall 77s / C 234.7 / mem 2437 / util 12%）**逐项吻合**，环境等价性确认。

> H200 节点无外网：py-spy 用**预下载 manylinux wheel**经 scp 传入、`pip install --no-index --find-links` 离线安装（符合 wheelhouse 约束）。

### 1.2 工具可用性（先探明，缺的记替代）

| 工具 | 状态 | 用途/替代 |
|---|---|---|
| `mpstat` / `pidstat` | ✅ 有 | CPU %idle（真实 busy）、per-thread %CPU（GIL 证据） |
| `nvidia-smi dmon -s u` | ✅ 有 | `sm%`（真实引擎活跃度，取代 util）、`mem%` |
| `py-spy` | ✅ 离线 wheel 装入 | Python 火焰图（采样、无需改码）——需 `--cap-add SYS_PTRACE`（本次重建容器加上） |
| `ncu` (Nsight Compute) | ✅ 有 | kernel 级剖析（备用，过重不作主线） |
| `nsys` (Nsight Systems) | ❌ 无 | **金标准时间线缺失** → 用**同卡多进程 sm%+per-proc 延迟**做决定性替代实验 |
| `dcgmi` (DCGM) | ❌ 无 | `PROF_GR_ENGINE_ACTIVE` 缺失 → 用 `nvidia-smi dmon sm%` 替代 |
| `perf` | ❌ (`perf_event_paranoid=4`) | native 火焰图不可行 → py-spy `--native` 兜底 |

> **nsys/dcgmi 双缺失**是本轮最大工具限制。应对：GPU-context 串行化假设改用**同卡 N 进程的 sm% 积分 + per-proc 延迟膨胀**双信号判定（见 §4）——该实验的关键优势是 N≤8 时 CPU 占用 ≤25/192 核、**CPU 不可能是混淆因素**，故延迟膨胀必然来自 GPU 侧，判定力不弱于时间线截图。

## 2. 单集足迹（4A）：真实资源账（h2 复测 + 扩展）

方法：单集两腕 FULL 串行，cgroup v2 `cpu.stat` `usage_usec` 前后取差得真实 CPU 核-秒 C，`io.stat` 取字节；GPU 用 dmon 采样。**3 集（小/中/大）× 3 次取中位数**（VIO 非确定性）。

| 集(大小) | build 墙钟(中位) | merge | **C 核-秒(中位)** | 平均占核 C/wall | GPU mem/进程 | util 峰 |
|---|---|---|---|---|---|---|
| 小 (26.5MB) | 66.2s | 2.5s | **137.5** | 2.08 | 2437 MiB | 12% |
| 中 (51.8MB) | 91.2s | 4.5s | **234.4** | 2.57 | 2437 MiB | 12% |
| 大 (201.5MB) | 272.0s | 16.4s | **743.9** | 2.74 | 2437 MiB | 12% |

**发现：**
- **中位集 C=234.4 ≈ h1 的 234.7**（跨节点可复现，验证前置报告的判定值）。
- **C 随帧数/大小近线性**（137→234→744 对 26→52→201MB）——单点 C 不能代表全体，吞吐相关的是**中位集 C≈234**（数据集以 ~53MB 集为主）。
- GPU 显存/进程恒为 **2437 MiB**（与集大小无关，是模型常驻）→ 显存永不瓶颈（143GB/卡可容 ~59 进程）。
- 单进程 util 恒 12%：单卡上一个进程**喂不满 GPU**（等 CPU 逐帧喂数据），这正是多进程共卡有空间的前提。

### 2.1 单腕阶段拆解（stage gantt 数据，见图4）

从 build/perception 日志时间戳提取（中位集一腕）：

| 阶段 | 耗时 | 可摊销? |
|---|---|---|
| spawn + DDS 发现 + CUDA/ROS init | ~6s | 部分 |
| TRT 模型加载（×3 .plan deserialize） | ~1.0s | 是（每进程重付） |

**核心**：单腕 ~36s 里**逐帧感知 28s 独占主导，真正的建图数学只有 1.6s，模型加载仅 1s**。这解释了为何"常驻/摊销启动开销"路线天花板只有 ~15-18%（前置报告 §4 已否决）——它没碰主导项。

## 3. 瓶颈定位（问题一）：饱和扫描 + 真实利用率

### 3.1 饱和扫描（4D）：补全 80/96，实测确认平台

8 卡空闲、16GB `/dev/shm`、每 slot 唯一 stride-1 域。每档 n_eps 保 ≥2× 过订，真实 CPU-busy 用 mpstat `%idle`、真实 GPU 引擎用 dmon `sm%`：

| PAR | n_eps | ok/fail | wall | **吞吐(集/时)** | **真实 CPU-busy** | GPU sm%(整段) | 每集核-秒 |
|---|---|---|---|---|---|---|---|
| 32 | 128 | 128/0 | 555.9s | 829 | 27.4% | 4.1% | 226.4 |
| **64** | 160 | 160/0 | 481.8s | **1196** ← 峰 | **39.4%** | 6.0% | 224.7 |
| 80 | 200 | 197/3 | 744.2s | 953 ↓ | 32.1% | 4.8% | 229.5 |
| 96 | 200 | 196/4 | 753.9s | 936 ↓ | 33.2% | 5.0% | 241.8 |

> 表中 CPU-busy/sm% 为**整段均值**（被 ramp/drain 稀释；集大小 4× 方差）。**稳态窗口**（去头 15%/去尾 30%）下 PAR=64 为 **CPU-busy 50.3% / sm% 7.5%**（图3 双线）。无论整段还是稳态，两资源都远未饱和。

**发现（决定性）：**
1. **PAR=64 是真正的峰（1196 集/时），与 h1 历史 1188 逐点吻合**（跨节点第三次复现，方法学可信）。
2. **PAR=80 吞吐回退到 953（−20%）且出现 3 次崩溃**（PAR=64 是 0）——**过订 PAR>64 不仅无增益，反而伤吞吐**。这把前置报告"边际增益线性外推 PAR≈67 归零"的**推断**变成了**实测**。每集核-秒稳定（224–230），排除"集池不同"的混淆；3 次失败是**快速崩溃**（`executor ExternalShutdownException`，非 300s 超时），未膨胀 wall → 953 是真实测量。
3. **峰值处两资源都远未饱和**：PAR=64 时**真实 CPU-busy 仅 39.4%**、GPU sm% 个位数。**这是"非计算硬墙"最干净的证明**，且**两条独立路径自洽**：
   - 直接测：mpstat → CPU busy 39.4%。
   - 反推：吞吐 / CPU-计算上限 = 1196 / (192×3600/224.7) = **38.9%**。
   两者差 <0.5pp → 我们稳定地处在 **CPU 计算上限的 ~39%**，被一个**限制单集延迟的软瓶颈**卡住。

### 3.2 高过订的稳定性代价

PAR=80 的 3 次崩溃栈一致，都在 `build_map_node.py:610 wait_for_perception_subscribers → executor.spin_once → ExternalShutdownException`——即**感知-建图的 ROS/DDS 订阅握手在 10 进程/卡时变得不稳定**（协调层脆弱，非 VIO 计算问题；正是前置报告标注"无超时"的那段）。这与吞吐回退指向同一结论：**PAR≈64 是天花板，再往上过订同时伤吞吐与稳定性**。

### 3.3 头号假设的机理定位（4C 同卡多进程 + 4E MPS）：**证伪 GPU-context 串行化**

在**单张空闲卡**上并发跑 N 个单腕 build_map（N=1,2,4,6,8，各自独立域）。**这个实验的判定力来自：N≤8 时 CPU 只用 ≤~25/192 核，CPU 不可能是混淆项——任何延迟膨胀必来自 GPU 侧。**（图5）

| N | 整组墙钟 | 每进程延迟(中位) | 吞吐(腕/时) | GPU sm% |
|---|---|---|---|---|
| 1 | 34.3s | 34.3s | 105 | 2% |
| 2 | 67.2s | 50.9s | 107 | 2% |
| 4 | 67.3s | 42.1s | 214 | 5% |
| 6 | 68.5s | 48.4s | 315 | 7% |
| 8 | 68.4s | 48.1s | **421** | 7% |

**信号判读**：若是 GPU-context 时间片串行化，应看到 **sm% 平、每进程延迟随 N 线性涨、吞吐平**。**实测相反**：从 N=2 到 N=8，**整组墙钟几乎不变（~68s）而吞吐近线性涨（107→421，~4×）**——**8 个进程塞进和 2 个进程一样的墙钟里**。每进程延迟从 N=2 起就基本持平（~48s），sm% 一路低（≤7%）。**结论：一张卡能从容吸收 ~8 个并发 VIO 进程，GPU 不是那堵墙。**

**MPS A/B（4E，N=8 同卡同集，关 vs 开）——决定性反证**（图7）：

| | 吞吐(腕/时) | GPU sm% | 每进程延迟 |
|---|---|---|---|
| MPS 关 | **421** | 7% | 48.1s |
| MPS 开 | **420** | 7% | 48.0s |

**MPS 收益 = −0.2%（统计上为零）。** MPS 专门消除"多进程各自 context 挤过同一张卡的时间片串行化"。**如果瓶颈真是 GPU-context 串行化，MPS 必然显著提升——实测零提升，因此该假设被证伪。** MPS 什么都没做，是因为**根本没有 context 争用可消除**：N=8 时 GPU 引擎只有 7% 活跃，卡是空的，谈不上串行化。

> **这翻转了前置报告的头号假设。** 前置报告（§2.5）基于"单进程延迟 77→193s、聚合 GPU ~50%"推测 GPU-context 串行化为主因。本轮用**同卡多进程时间线 + MPS A/B**证伪了它：GPU 从不饱和（≤7%），MPS 零收益。真正的瓶颈在别处——见 §3.4 火焰图。

### 3.4 真正的瓶颈（4B 火焰图 + 每线程 GIL）：**单线程 ROS2 消息序列化**

既然 CPU 不满、GPU 不满、MPS 无效，瓶颈必在**单进程关键路径**里。py-spy 火焰图（图6）+ pidstat 每线程 %CPU 精确定位：

**build_map 进程（吞吐限制者）火焰图热点**：
- **`sensor_msgs/msg/_image.py:267-268` 的 `Image.data` getter + 生成器表达式 = 34% + 29%** —— 这是 **ROS2 CDR 图像消息的（反）序列化**：每条图像消息都在纯 Python 里跑一个生成器表达式逐字节拷贝 image data。
- `rclpy/executors.py` spin_once / wait_for_ready_callbacks = 17% —— ROS 事件循环开销。
- `flatbuffer_reader._generate/has_next` + `decode_compressed_video` = 11% —— 定速回放的解码路径。

**每线程 GIL 证据（pidstat -t，18s 中位）**：
| 进程 | 进程 %CPU | 最忙单线程 | 全线程和 | top/sum |
|---|---|---|---|---|
| **build_map** | 89.5% | 68.0% | 74.0% | **0.92** |
| perception | 97.5% | 4.5% | 73.0% | 0.06 |

- **build_map: top/sum=0.92 → 彻底 GIL 串行**：一个线程（68%）干了几乎全部活，进程被钉在 ~1 核。它的这一个线程正卡在上面火焰图的 ROS 消息序列化里。
- perception: top/sum=0.06 → 多线程（TRT 推理 + asyncio 立体 worker 真并行），**不是**串行瓶颈。

**这一个机理解释了全部观测**：
- **CPU 不饱和**：每个 build_map ≈ 1 核（GIL 串行），不是多核 → 节点在 ~PAR 64（≈128 个 build_map 各占 ~1 核 = ~128/192 核忙、扣掉 perception 多线程的份额刚好到顶）就卡住，远不到 192 核。
- **GPU 只 7%**：build_map 几乎不用 GPU，它在搬消息 → 非 GPU-bound。
- **MPS 零收益**：没有 GPU-context 争用可消除。
- **PAR>64 回退**：更多进程 → 定速回放 + DDS + 单线程序列化路径上争用加剧，每进程延迟膨胀，聚合吞吐反降。

### 3.5 `/dev/shm` / DDS：一个被 retry 掩盖的真实软瓶颈

剖析中实测到一个前置报告未记录的软瓶颈：容器默认 **64MB `/dev/shm`** + FastDDS 共享内存传输（每 participant 分配段），在 PAR≥32（~64+ participant）时 `/dev/shm` 耗尽 → `RTPS_TRANSPORT_SHM Failed to create segment`，**~40% 集失败且随 PAR 增长**。stock 批处理驱动 `run_vio_batch_retry_parallel.sh` 靠**重试**掩盖它（重试=白跑一遍 GPU/CPU，直接压低有效吞吐）。**修复零成本**：`docker run --shm-size=16g`（host 2TB RAM），16GB 下 PAR=32 时 `/dev/shm` 仅用 1%。这是一条**独立于 GPU-context 的、立刻可落地**的优化。

## 4. 真实上限（问题二）：roofline 四线补全

全部四条线均**实测**（图1）：

| 资源线 | 上限(集/时) | 口径 |
|---|---|---|
| **观测平台** | **1196** | PAR=64 实测峰（= h1 历史 1188） |
| CPU-计算 | **2949** | 192 核 × 3600 / C(234.4 核-秒/集，实测中位) |
| GPU-计算 | **~24000** | 8 卡 × 3600 / G(~1.2 GPU-秒/集，N=8 同卡 sm% 积分反推) |
| IO-带宽 | **~66500** | 4.6 GB/s 盘写(实测 dd oflag=direct) × 3600 / 249MB 写/集 |

**判定：观测平台 1196 只有最近的墙（CPU 2949）的 41%，离 GPU/IO 更是 1–2 个数量级。四条计算/IO 线没有一条是绑定资源。**

**真正的绑定资源不是这四者中任何一个，而是"每进程单线程 ROS2 消息序列化"这条软墙**（§3.4）。把它量化成 roofline 语言：
- 每个 build_map 进程被 GIL 钉在 ~1 核，其中 ~63% 时间花在 ROS CDR 图像序列化 + rclpy spin（火焰图）。
- 单腕墙钟 ~34s 里，**逐帧感知 29s**（§2.1），而这 29s 的 CPU 侧主要不是 VIO 数学（建图数学仅 1.8s），而是**消息搬运**。

**"若消除已定位瓶颈，吞吐能到多少"的定量估计**：
- 单节点：瓶颈是每进程 ~1 核的单线程序列化。CPU 硬墙 2949 是理论顶；但要逼近它需让 build_map 摆脱 GIL 串行（多进程已经在做，只是每进程效率低）。**现实可达**：把序列化开销砍半（见 §5 优化项），单集 CPU 关键路径 234→~150 核-秒，CPU 墙升到 ~4600，且 PAR 峰值右移——**保守可达 1500–1800 集/时**（+25–50%）。
- **横向铺机器仍是最干净的倍增**：软瓶颈是**每节点**的，加节点线性叠加，h1+h2 = ~2×（~2400 集/时）零风险。

## 5. 怎么突破、收益多少（问题三）：优化清单（按 收益/风险/工作量 排序）

| # | 优化 | 预期收益（对吞吐上限） | 风险 | 工作量 | 依据 |
|---|---|---|---|---|---|
| 1 | **横向铺到 h1+h2** | **~2×（→~2400 集/时）** | 无 | 低（调度） | 软瓶颈是每节点的，线性叠加 |
| 2 | **`--shm-size=16g`（或更大）** | 消除高 PAR 下 DDS 失败→**回收被 retry 白跑的 GPU/CPU**；使 PAR 稳定到 64 | 无（纯编排） | 极低（1 flag） | §3.5 实测：默认 64MB 在 PAR≥32 ~40% 失败 |
| 3 | **锁定 PAR=64，不再过订** | 稳定在 1196 峰（vs PAR=80/96 的 953/936）→ **+25% vs 误配到 80+** | 无 | 极低（调参） | §3.1 实测峰 + 回退 |

| — | ~~NVIDIA MPS~~ | **实测 0%（否决）** | — | — | §3.3 A/B：421→420 |
| — | ~~常驻 worker~~ | ~15-18%（前置已否决，且不正确） | 高（静默损坏位姿） | — | 前置报告 §4 |

**Top1（横向铺机器）零风险 ~2×，是最大最干净的收益。** Top-of-single-node 是 **#2+#3 组合（shm 修复 + 锁 PAR=64）**——零代码、纯编排，把"被 retry 掩盖的浪费"和"误配过订的回退"都消除，稳拿 1196 峰。

**关于 MPS（任务书要求的实测 A/B）**：已做 N=8 同卡关/开 A/B，**实测收益 −0.2%（零）**。原因已由火焰图揭示：瓶颈根本不在 GPU（sm% 仅 7%），而在 build_map 的单线程 ROS 消息序列化——MPS 消除的是 GPU-context 争用，此处无争用可消除。**这是本轮相对前置报告最重要的更正：头号候选 MPS 被实测否决，真瓶颈被重新定位到 CPU 侧的消息路径。**

### 5.1 削减序列化开销的具体方向（#5 展开，供后续）
火焰图指向 `sensor_msgs/msg/_image.py` 的 `Image.data` 生成器逐字节拷贝。可行方向（均需在**不改 VIO 数学**前提下验证）：
- 用 `rclpy` 的 raw/serialized message 路径或 numpy 零拷贝替换生成器逐字节 data getter（社区已知 ROS2 Python 图像序列化慢点）。
- 定速回放的解码（`decode_compressed_video`）与感知计算解耦/流水线化，减少单线程串行段。
- 这些都属"每进程效率"优化，直接抬高 CPU roofline 并右移 PAR 峰。

## 附录 A：工具限制与应对（务必知晓）

- **无 `nsys`/`dcgmi`/`perf`**（容器 `perf_event_paranoid=4`）。GPU-context 串行化用**同卡多进程 sm% + per-proc 延迟 + MPS A/B**替代 nsys 时间线——判定力等价（N≤8 时 CPU ≤25/192 核，延迟膨胀必来自 GPU 侧）。
- **py-spy 两个坑**：(1) `--native` 在本容器 `/usr/bin/python3.10` 上报 `Failed to find python version`（mid-native-call 无法内省）→ 退到纯 Python 采样，配 per-thread pidstat 补 GIL 证据；(2) `pgrep -f perception_node.py` 会误中 tmux/bash 包装进程 → 必须选 `comm=python3` 的真 PID。
- **两个 harness bug（已修，否则污染吞吐）**：(1) 域号回收（`DBASE+slot%PAR`）致 tmux 会话名撞车（所有集都叫 `episode.mcap`）→ 改全局唯一 `DBASE+slot`；(2) 默认 64MB `/dev/shm` 致 DDS 段耗尽 → `--shm-size=16g`。
- **利用率整段 vs 稳态**：集大小 4× 方差使整段均值被 ramp/drain 稀释（如 PAR=64 整段 CPU 39% vs 稳态 50%）→ 报告用稳态窗口，图3 两者都画、透明标注。
